# Dial Control — Contributor & AI Agent Guidelines

Welcome to **Dial Control**. This document serves as the single source of truth, operating manual, and comprehensive architectural reference for all developers and AI agents working on this codebase.

---

## 1. Core Philosophy & Primary Directive

### 🎯 Standalone Cross-Platform Product
The goal of this project is to build and ship a **standalone desktop application** that can be installed and run out-of-the-box by **anyone on Linux, macOS, and Windows** with full feature parity.

### 🌐 Cross-Platform First, Edge-Case Fallbacks Second
- **Do NOT build features solely for a specific laptop or desktop environment** (e.g., GNOME on Wayland).
- **Architecture Flow**:
  1. **Define Universal Core**: Design clean, platform-agnostic abstractions (Rust traits in `src-tauri/src/platform/traits.rs`).
  2. **Implement Platform Backends**: Build standard implementations for Windows (Win32/WASAPI), macOS (CoreAudio/IOKit/Cocoa), and Linux (WirePlumber/Pulse/sysfs).
  3. **Add Desktop Environment Edge-Case Fallbacks**: Only after the universal base is in place, layer in graceful workarounds for environment quirks (e.g. GNOME Wayland sandboxing, Mutter D-Bus, AT-SPI) without breaking or polluting other platforms.

### 🛡️ Regression Prevention & Zero-Breakage Mandate
- **NEVER BREAK PREVIOUSLY WORKING PLATFORMS OR FEATURES**:
  - Whenever adding features, refactoring, or optimizing for one OS (e.g., implementing macOS support or tuning Linux), you **must ensure nothing previously built on Windows or Linux breaks**.
  - New agent sessions must review the architecture and testing guidelines before making modifications.
  - Before committing or concluding any turn, run local compilation checks for all supported targets: Linux (`cargo check`), Windows MSVC (`cargo check --target x86_64-pc-windows-msvc`), macOS (`CC_aarch64_apple_darwin=clang cargo check --target aarch64-apple-darwin`), and frontend (`npm run build`).

### 🔍 Research Before Probing (Internet First)
- **Do not guess or run trial-and-error shell commands** on the host machine to figure out how OS-level features work.
- **Use the internet**: Search the web, consult official OS APIs, and inspect how established cross-platform applications and Rust crates solve problems (e.g., `volumecontrol`, `brightness`, `x-win`, `active-win-pos-rs`, `enigo`, `winit`).
- When researching, verify best practices and compatibility across Windows, macOS, and Linux.

## 5. Subsystems Deep-Dive: Working Principles & Mechanics

### 5.1 CMF Buds Pro 2 Rotary Dial Interception

#### Hardware Profile
The CMF Buds Pro 2 rotary dial and smart case have **no proprietary Bluetooth protocol**. They implement standard Bluetooth AVRCP (Audio/Video Remote Control Profile):
- **Rotation**: Emits standard AVRCP Volume Up (`KEY_VOLUMEUP`) and Volume Down (`KEY_VOLUMEDOWN`) commands to the host OS.
- **Center Click**: Emits standard media key events (`KEY_PLAYPAUSE`, `KEY_PLAYCD`, `KEY_PAUSECD`, or `KEY_VOICECOMMAND`).

#### Linux Backend (`src-tauri/src/platform/linux/dial.rs`)
1. **Hardware Click Grabber (`start_input_grabber`)**:
   - Parses `/proc/bus/input/devices` to locate the event handler for `"CMF Buds Pro 2"` (or generic `"AVRCP"`).
   - Opens the device node (`/dev/input/eventX`) via `evdev::Device::open`.
   - **Exclusively grabs the device** (`device.grab()`). This is critical: without the exclusive grab, clicking the dial would simultaneously toggle media playback in Spotify/YouTube while trying to open the HUD.
   - Intercepts clicks with a 500ms software debounce.
   - If scroll mode is active $\to$ exits scroll mode.
   - If HUD is closed $\to$ opens HUD.
   - If HUD is already open $\to$ dispatches `dial:click` to trigger the selected slice action.

2. **BlueZ AVRCP Volume Listener (`start_bluez_listener`)**:
   - Subscribes to system D-Bus signals for `org.freedesktop.DBus.Properties.PropertiesChanged` on interface `org.bluez.MediaTransport1`.
   - Volume changes arrive as raw 0..127 integer values (`u16`).

3. **Stateful Volume Locking & Echo Suppression**:
   - **The Problem**: When navigating the HUD menu, scrolling, or adjusting brightness, turning the earbud dial would naturally alter system audio playback volume.
   - **The Solution**: Lock audio volume at the pre-existing level (`locked_vol`).
   - **Headroom Clamping (`8..119`)**: Raw volume is clamped to the range `8..119`. If volume is at 100% (127), turning CW produces no change (it cannot exceed 127). If volume is at 0%, turning CCW produces no change. Clamping to 8..119 guarantees that turning in either direction always has sufficient headroom (at least 8 raw units) to register on D-Bus.
   - **Stateful Echo Cancellation**:
     - When the dial is turned, `new_vol` moves away from `baseline`.
     - Dial Control emits the user action (menu rotation or scroll tick).
     - It immediately sets `restore_pending = true` and calls `org.bluez.MediaTransport1.Set("Volume", baseline)` directly over D-Bus (< 1ms).
     - When BlueZ restores the volume to `baseline`, it emits a `PropertiesChanged` signal back onto D-Bus.
     - **The Echo Filter**: If `|new_vol - baseline| <= 3` OR (`restore_pending` is true and `new_vol` moved towards baseline), the incoming event is **swallowed completely**. No rotation event is emitted.
     - Only movements *away* from baseline in the active direction generate user actions.

#### Windows Backend (`src-tauri/src/platform/windows/dial.rs`)
- Uses a low-level keyboard hook (`WH_KEYBOARD_LL`) in a dedicated message pump thread with an automatic watchdog timer (`SetTimer`) and re-registration recovery loop.
- **Microsecond Non-Blocking Execution**:
  - Windows `LowLevelHooksTimeout` (100–300ms) silently kills hooks if callbacks block or acquire contended locks.
  - Global state is held in lock-free `std::sync::OnceLock<Arc<AtomicBool/I32>>` with zero mutexes or `RwLock`s.
  - All heavy work (GUI display, Tauri event emission, D-Bus/Win32 calls) is strictly dispatched to background worker threads (`thread::spawn`).
- **Complete KeyDown and KeyUp Interception**:
  - The hook checks both `WM_KEYDOWN`/`WM_SYSKEYDOWN` and `WM_KEYUP`/`WM_SYSKEYUP`.
  - For `VK_MEDIA_PLAY_PAUSE`, `VK_PAUSE`, and `VK_MEDIA_STOP`: both KeyDown and KeyUp return `1`. Consuming KeyUp is critical to prevent media players (Spotify, YouTube, Chrome) from receiving a play/pause toggle on key release!
  - For `VK_VOLUME_UP` and `VK_VOLUME_DOWN`: while HUD or scroll mode is active, both KeyDown and KeyUp return `1` to prevent the OS volume slider or beep popup from triggering.
  - When HUD is closed and not in scroll mode, volume keys pass through to `CallNextHookEx` so system volume works normally.
- **Win32 Foreground Window Activation**:
  - Background processes on Windows are restricted by `LockSetForegroundWindow`.
  - In `do_show_hud` (`src-tauri/src/lib.rs`), Tauri's `window.set_focus()` is paired with native Win32 `ShowWindow(hwnd, SW_RESTORE)`, `SetForegroundWindow(hwnd)`, and `SetWindowPos(hwnd, HWND_TOPMOST, ...)` so the HUD reliably pops up over fullscreen windows.

#### macOS Backend (`src-tauri/src/platform/macos/dial.rs`)
- Uses a global CoreGraphics Event Tap (`CGEventTapCreate`) listening to `NX_SYSDEFINED` events (subtype `NX_SUBTYPE_AUX_CONTROL_BUTTONS = 8`).
- Intercepts system auxiliary keys:
  - `NX_KEYTYPE_SOUND_UP` (0) $\to$ CW dial rotation (`direction: 1`).
  - `NX_KEYTYPE_SOUND_DOWN` (1) $\to$ CCW dial rotation (`direction: -1`).
  - `NX_KEYTYPE_PLAY` (16) $\to$ Media center click.
- **Hardware-Level Event Consumption**:
  - When volume lock is active (`is_hud_open` or `is_scroll_mode`):
    - Emits `dial:rotate` or `scroll:tick` to the frontend.
    - **Returns `null_mut()` from the callback**: This drops the event, instructing macOS to completely discard the keypress. System audio does not change and the macOS volume bezel does not appear. Zero echo feedback loop!
    - For center click: returns `null_mut()` so Apple Music or Spotify does not play/pause while opening or navigating the HUD.
  - When in natural volume mode (`locked_vol < 0`), returns the event pointer so macOS handles hardware volume changes natively.

### 5.2 Scroll Mode

#### Purpose
Turns the rotary dial into a continuous, physical mouse scroll wheel for long documents, code, web feeds, and YouTube Shorts.

#### Architecture
- **Linux (`src-tauri/src/platform/linux/input.rs`)**:
  - Emulates kernel relative mouse wheel events via `/dev/uinput` (`LinuxInput.emit_scroll`).
  - Emits `InputEvent::new(EventType::RELATIVE, RelativeAxisType::REL_WHEEL.0, delta)`.
  - CW rotation $\to$ scroll down (`delta: -1`).
  - CCW rotation $\to$ scroll up (`delta: 1`).
- **Windows (`src-tauri/src/platform/windows/input.rs`)**:
  - Emulates mouse wheel using Win32 `SendInput` with `MOUSEEVENTF_WHEEL`.
- **macOS (`src-tauri/src/platform/macos/input.rs`)**:
  - Emulates mouse wheel using CoreGraphics `CGEventCreateScrollWheelEvent2(null_mut(), kCGScrollEventUnitLine, 1, delta, 0, 0)`.
  - Posts event directly to `kCGHIDEventTap`.

#### Focus & Window Management Lifecycle
1. User selects "Scroll Mode" in HUD.
2. Frontend sets mode to `"scroll"`, displaying `"ROTATE TO SCROLL"` in the center.
3. After 850ms, frontend calls `close_hud_for_scroll`, which hides the HUD window.
4. **Why the HUD window MUST be hidden**:
   - On Wayland, Windows, and macOS, if any application window is visible and focused, mouse wheel events will be directed to that window or blocked from reaching the underlying browser/editor.
   - Hiding the HUD returns focus directly to the underlying application.
5. Cross-platform OS notification sent on entry:
   - Linux: `notify-send -a "Dial Control" "Scroll Mode Active" "Rotate dial to scroll • Click dial or shortcut to exit"`
   - Windows: WinRT `ToastNotificationManager` via PowerShell with `CREATE_NO_WINDOW`.
   - macOS: AppleScript notification (`display notification "Rotate dial to scroll • Click dial or shortcut to exit" with title "Scroll Mode Active"`).
6. To exit scroll mode:
   - Click the dial center button, or press the global toggle shortcut.
   - Backend calls `do_stop_scroll_mode`, sends exit notification (`"Scroll Mode Exited"`), and restores volume lock state to `-1`.

### 5.3 Brightness Control

#### Linux Mutter `GetResources` Live Brightness
1. **The Modern Laptop / OLED Problem**:
   - On modern OLED laptops (e.g. Samsung SDC panels on Intel), `/sys/class/backlight/intel_backlight/brightness` is a dummy ACPI driver stuck permanently at `400/400` (100%).
   - GNOME Shell does not write to sysfs; it controls OLED brightness via Mutter's internal PWM/LUT display server configuration.
2. **Reading System Brightness (`get_mutter_resources_brightness`)**:
   - Queries `org.gnome.Mutter.DisplayConfig` on session D-Bus method `GetResources`.
   - Iterates over active display outputs (e.g. `eDP-1`), locating the `backlight` property.
   - Extracts current and max values (e.g., `0..100`), calculating the exact current brightness percentage (working accurately down to 0% on pure black OLED screens).
   - Fallback: `/sys/class/backlight/` sysfs for non-GNOME/X11 compositors.
3. **Adjusting Brightness (`step_brightness`)**:
   - Emulates hardware keyboard brightness keys (`KEY_BRIGHTNESSUP` / `KEY_BRIGHTNESSDOWN`) via `/dev/uinput`.
   - GNOME Shell catches the hardware key event, adjusts Mutter display brightness in native 5% steps, and displays the native GNOME OSD brightness slider.
4. **UI Synchronization**:
   - The frontend queries `get_system_brightness` only when the user selects the Brightness mode on the dial. There is **zero background polling**.

#### Windows Dual-Engine Brightness (`src-tauri/src/platform/windows/brightness.rs`)
1. **External Monitors (DDC/CI via `dxva2.dll`)**:
   - Dynamically loads `dxva2.dll` at runtime via `LoadLibraryW`.
   - Calls `GetMonitorBrightness` on physical monitors for instant (< 1ms), live hardware backlight queries with zero process spawning.
2. **Internal Laptop Screens (WMI `WmiMonitorBrightness`)**:
   - Queries `root/wmi:WmiMonitorBrightness.CurrentBrightness` via non-interactive PowerShell with `CREATE_NO_WINDOW`.
   - **Continuous Background Poller**: Runs a 1.5s background polling loop that continuously updates `cached_brightness`. This guarantees that brightness adjustments made outside the app (via laptop Fn keys, Windows Action Center slider, or Settings) immediately synchronize with Dial Control.
   - **Hardware Transition Protection (`last_set_time`)**: When the user adjusts brightness through Dial Control, polling is suspended for 2.5s to prevent intermediate hardware sensor readings from overriding user intent.
   - **Stepping Guarantee**: `step_brightness()` always steps relative to `get_brightness()`, ensuring the display never jumps or snaps back to stale values.

#### macOS DisplayServices Dynamic Brightness (`src-tauri/src/platform/macos/brightness.rs`)
- Dynamically loads `/System/Library/PrivateFrameworks/DisplayServices.framework/DisplayServices` via `dlopen`/`dlsym`.
- Uses `DisplayServicesGetBrightness` and `DisplayServicesSetBrightness` on `CGMainDisplayID()`.
- Dynamic loading eliminates fatal linker errors on modern macOS SDKs while giving 100% native backlight control on both Apple Silicon and Intel Macs.
- Fallback to `brightness` CLI if DisplayServices symbols are unavailable.

### 5.4 Active Window Context Detection

#### Purpose
Automatically switches the radial wheel's active profile based on the foreground application (e.g., VS Code profile when coding, Chrome/Brave profile when browsing, Spotify profile when listening to music).

#### Linux Implementation
1. **Wayland Sandboxing Challenge**:
   - Under Wayland, client applications are forbidden from inspecting other clients' window titles or process IDs for security reasons.
2. **GNOME Shell Extension Integration**:
   - Bundles the lightweight GNOME extension `focused-window-dbus@flexagoon.com` in `resources/gnome-extension/`.
   - The extension listens to `global.display.focus_window` inside Mutter and broadcasts window metadata over user session D-Bus:
     - Bus: `org.gnome.Shell.FocusedWindow`
     - Object: `/org/gnome/Shell/FocusedWindow`
     - Properties: `wm_class`, `title`
3. **Multi-Compositor Fallbacks**:
   - Hyprland: `hyprctl activewindow -j`
   - Sway: `swaymsg -t get_tree`
   - X11: `_NET_ACTIVE_WINDOW` root window atom via `x11-dl`.
4. **Profile Matching (`App.tsx`)**:
   - Checks `match_patterns` in `config/profiles.json` against `wm_class`, `app`, and window `title`.

### 5.5 HUD & Settings Windows Architecture

#### Multi-Window Geometry & Centering
- **HUD Window (`hud`)**:
  - `500x500`, borderless, transparent, frameless, always-on-top.
  - Every time `do_show_hud` is called:
    - Calls `window.center()`.
    - On Linux GTK: calls `gtk_w.set_position(gtk::WindowPosition::Center)`, `gtk_w.set_accept_focus(true)`, and `gtk_w.present()`. This guarantees the HUD is always centered on whichever monitor is active, regardless of Wayland compositor quirks.
- **Settings Window (`settings`)**:
  - `1080x680`, minWidth `900`, minHeight `550`.
  - 3-column layout: Profiles list $\to$ Wheel slices $\to$ Slice inspector & action settings.
  - Containers use `shrink-0` on navigation columns and `overflow-x-auto` to prevent controls from clipping on scaled displays (125%-150% DPI).
- **Preventing Window Destruction**:
  - Both `settings` and `hud` intercept `tauri::WindowEvent::CloseRequested` in `lib.rs` and call `api.prevent_close()` followed by `window.hide()`. Desktop utility windows are hidden, never destroyed.

## 6. What Was Considered and Rejected (Archived Decisions)

Understanding what failed in earlier builds prevents regression into past mistakes:

### ❌ 1. Floating Mini-Pill Window for Scroll Mode (`scroll_pill`)
- **What was tried**: A tiny floating pill window (`200x48`) showing `"SCROLL MODE"` while scrolling.
- **Why it failed**:
  - On Wayland, creating additional windows stole input focus from the application being scrolled (browser/IDE).
  - Multi-window race conditions caused the pill to linger or re-center over the main HUD.
  - Compositors placed the pill at unpredictable coordinates depending on multi-monitor setups.
- **Adopted Replacement**: Native OS notifications (`send_os_notification`) on entry and exit. Zero window clutter, zero focus loss.

### ❌ 2. Fullscreen Screen Edge Overlay (`scroll_overlay`)
- **What was tried**: A transparent fullscreen border outline around the screen indicating scroll mode.
- **Why it failed**:
  - On Wayland/Mutter, transparent fullscreen windows frequently render as an opaque black screen due to compositor alpha-channel handling.
  - The transparent window acted as an active XDG shell surface, intercepting mouse clicks and preventing the user from interacting with the underlying webpage.
- **Adopted Replacement**: No overlay window. Native notifications + clear visual indicator in the HUD before transition.

### ❌ 3. Raw Global `Space` and `Escape` Key Grabs for Exiting Scroll
- **What was tried**: Registering global shortcuts on `Space` and `Escape` to quickly exit scroll mode.
- **Why it failed**:
  - `Space` and `Escape` are universal application shortcuts (e.g., play/pause and exit fullscreen in YouTube Shorts, video players, and games).
  - The global grab broke basic web player controls.
- **Adopted Replacement**: Center-click on the rotary dial or the dedicated global toggle shortcut (`Super+Shift+D`).

### ❌ 4. Dual-Channel Volume Restoration (`wpctl` + BlueZ in a loop)
- **What was tried**: Restoring locked volume by simultaneously calling `wpctl set-volume` in a spawned thread AND `proxy.call_method("Set", Volume)` on BlueZ on every single rotation tick.
- **Why it failed**:
  - Created an **infinite feedback echo loop**. Spawning `wpctl` child processes on every tick caused out-of-order execution.
  - WirePlumber synchronized back to BlueZ, which emitted duplicate `PropertiesChanged` signals.
  - Floating percentage rounding (`62%` $\to$ raw `79` vs WirePlumber raw `71`) caused a 8-unit discrepancy that exceeded tolerance filters.
  - The listener misinterpreted its own restore signal as a reverse turn, causing **CW rotation to snap back to the first option** and **CCW rotation to double-step**.
- **Adopted Replacement**: Single async D-Bus call to BlueZ `MediaTransport1` (< 1ms). Direct raw integer tracking (`baseline_raw`). Strict echo cancellation that swallows any signal moving towards baseline. WirePlumber audio volume is restored once on exit.

### ❌ 5. Direct Writing to `/sys/class/backlight`
- **What was tried**: Writing brightness percentages to `/sys/class/backlight/*/brightness` via shell scripts or file I/O.
- **Why it failed**:
  - Requires elevated root permissions.
  - Bypasses desktop environment state, causing GNOME's slider to fall completely out of sync.
  - Fails on modern OLED panels where `/sys/class/backlight` is a dummy driver.
- **Adopted Replacement**: Mutter D-Bus `GetResources` for reading + `/dev/uinput` brightness key emulation for writing.

## 7. Development & Build Workflow

### ⚠️ Mandatory Production Build Procedure
**NEVER use raw `cargo build --release` to generate final binaries.**
Raw `cargo build` does NOT build or inline the React frontend. It leaves the binary pointing to `http://localhost:1420`, breaking when the dev server is offline.

**Correct Production Build Sequence**:
```bash
# 1. Compile frontend and embed assets into standalone release binary:
npx @tauri-apps/cli build --no-bundle
# (or: npm run build && cargo build --release --manifest-path src-tauri/Cargo.toml)

# 2. Install executable to the local launcher path:
install -m 755 src-tauri/target/release/dial-control bin/dial-control

# 3. Assemble distribution packages (.deb, .rpm, .pkg.tar.zst, .AppImage):
./scripts/build-packages.sh
```
